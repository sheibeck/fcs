# Pitfalls Research

**Domain:** Greenfield rebuild + AWS→Firebase migration of a live, paying-subscriber SPA (Fate Character Sheet v2.0)
**Researched:** 2026-08-31
**Confidence:** HIGH for migration-mechanics and Firebase-platform claims (grounded in official docs / current community writeups, cross-checked); MEDIUM for print-fidelity and PeerJS-on-Cloud-Run specifics (fewer authoritative sources, rapidly-evolving platform behavior); HIGH for rewrite-trap and solo-maintainer framing (well-established, codebase-grounded).

This document is scoped to what THIS project will specifically break on — a live app with an unknown-but-likely-large total registered user base (see Pitfall 1) being rebuilt from scratch and migrated from AWS (Cognito/DynamoDB/Lambda) to Firebase (Auth/Firestore/Cloud Functions/Hosting), with print-fidelity character sheets as the non-negotiable core feature and a solo maintainer on Windows. It intentionally excludes generic "how to use Firestore" tutorials.

**Scale note (important, corrects an assumption used elsewhere in this project's research):** `PROJECT.md` cites "~259 active users / ~1.3k views per 7 days" — that figure is a **Google Analytics active-user count over a 7-day window**, not the total number of registered accounts. The true migration surface is the full Cognito user pool + every `owner_id` with rows in DynamoDB, which is very likely materially larger than 259 (anyone who signed up once, or subscribed and later went quiet, is invisible to a 7-day GA window but still has an account, saved characters, and possibly an active, auto-renewing Stripe subscription). Every pitfall below that references "users" means the full registered/record base, not the GA-active subset — this distinction is significant enough to warrant its own pitfall (Pitfall 1) and shows up again in the Cognito-import (2), bulk-migration (4), and Stripe-continuity (5) pitfalls.

**Rebuild-scope framing (also important):** This is a from-scratch rebuild, not an in-place migration — nothing about the old codebase's internal architecture, data-access patterns, or component structure needs to be preserved. Several of the old app's internals (the `eval()`-based `getVal`/`setVal` path-access pattern, the DynamoDB single-table/GSI shape, the manual per-sheet component-registration list) are known-fragile or outright broken and should be **redesigned, not reproduced** — a more stable, idiomatic pattern on the new stack is always preferable to faithfully porting a legacy internal. Accordingly, the pitfalls below carry exactly **two hard constraints**, and every "rewrite trap" / parity-related pitfall is scoped to protecting those two, not to fidelity with the old implementation:

1. **User-facing functionality and print-fidelity sheet rendering must reach parity** with the current app — a subscriber's new experience must do what the AWS version does, including printing the way it prints today. How that's implemented underneath (state management, data-access pattern, component structure, even the DynamoDB→Firestore schema shape) is entirely open.
2. **Zero data loss** — whatever new data model is chosen must be reachable by a documented, verifiable migration mapping from every existing DynamoDB record, for the *full registered user base* (see the scale note above), not just currently-active users.

Where a pitfall below discusses redesigning a data model or replacing a legacy pattern, that redesign is encouraged, not a risk to avoid — the risk being flagged is always about the two hard constraints (parity + zero data loss), never about deviating from the old implementation.

## Critical Pitfalls

### Pitfall 1: Planning the migration against the GA "active users" number instead of the true total account/record count

**What goes wrong:**
Every downstream migration decision — how long a bulk Cognito export/import takes, how much Firestore bulk-write throughput is needed, how many Stripe customer records need `customer_id`→UID remapping, how big the reconciliation/verification pass is, what the realistic maintenance-window duration should be — gets sized against "~259 users" because that's the only number readily visible (Google Analytics). GA's active-user count only reflects people who *visited* in the measured window; it says nothing about the size of the Cognito user pool or the number of distinct `owner_id` values with rows in DynamoDB. A user who signed up two years ago, saved a dozen characters, and hasn't logged in since — but is still an active, auto-renewing Stripe subscriber, or simply still owns data that must not be lost — is invisible to GA and therefore invisible to a migration plan built off that figure. If the true total is, say, 5–10x the GA figure (plausible for any subscription product with normal churn/dormancy patterns), every capacity, timeline, and cost estimate built on 259 is wrong by the same multiple, and the gap is discovered mid-migration rather than during planning.

**Why it happens:**
GA active-users is the number that's already on hand and easy to cite, while the authoritative counts (Cognito user pool size, distinct `owner_id` count in DynamoDB) require an explicit query against the actual backend systems — a step that's easy to skip when a plausible-looking number is already sitting in an analytics dashboard.

**How to avoid:**
Before any migration design work (before Pitfalls 2–5 below can be sized correctly), run the actual counts directly against the source systems: `aws cognito-idp list-users` (paginated) or the Cognito console's user-pool count for the true total registered-account count, and a DynamoDB scan (or, cheaper, a query against the `type` GSI per `object_type`, or `DescribeTable`'s approximate item count) for the true total record count and distinct `owner_id` count. Cross-reference the two — every `owner_id` in DynamoDB should map to a Cognito user (and vice versa for anyone with saved data), and any mismatch is itself a data-quality issue worth knowing about before migrating. Re-baseline every subsequent estimate (bulk-import batch counts, Firestore write-throughput ramp planning, reconciliation-pass scope, Stripe customer-mapping list, maintenance-window duration) against these real numbers, not the GA figure. Treat this as a required, gating first step of the migration-design phase, not a nice-to-have — it directly determines how the zero-data-loss constraint (hard constraint #2, above) must be scoped.

**Warning signs:** Any migration timeline, cost estimate, or capacity plan that cites "259 users" without a corresponding Cognito/DynamoDB count to back it up; discovering during the actual bulk export that the row/user count is a large multiple of what was planned for.

**Phase to address:** Migration-design phase, as the explicit first step before Pitfalls 2, 4, and 5 (Cognito import, bulk-migration throughput, and Stripe continuity) can be sized or sequenced correctly.

### Pitfall 2: Assuming Cognito password hashes can be exported and imported into Firebase Auth — and underestimating how many *dormant* accounts that decision affects

**What goes wrong:**
Teams plan the auth migration as "export users from Cognito, import into Firebase Auth" and only discover mid-project that Cognito does not expose password hashes at all — Cognito's SRP-based auth flow never stores or reveals a portable hash you can hand to `auth.importUsers()`. Firebase Auth's bulk import (`firebase auth:import` / Admin SDK `importUsers`) supports importing pre-hashed passwords, but only for algorithms it recognizes (BCRYPT, SCRYPT, STANDARD_SCRYPT, HMAC-*, PBKDF2, MD5/SHA family) — Cognito's SRP verifier is not one of them and AWS does not export it. This problem compounds with Pitfall 1's scale correction: if the true registered-account count is much larger than the ~259 GA-active figure, a large fraction of those accounts are, by definition, dormant (haven't logged in during the GA measurement window) — and a forced-password-reset migration strategy disproportionately fails exactly this group, since a dormant user is also the least likely to notice or act on a "please reset your password" email months or years after their last visit. A migration plan that only accounts for the ~259 "recently active" users risks silently stranding every dormant-but-real account (including any that are still paying via Stripe, see Pitfall 5) with no working login path at all — a direct violation of the zero-data-loss constraint in spirit, since a user who can never log in again has effectively lost access to their data even though the rows still technically exist in Firestore.

**Why it happens:**
Most "migrate users to Firebase" writeups assume a traditional password-hash-in-a-database system (bcrypt/scrypt/PBKDF2), where hash export + `importUsers` genuinely is a zero-friction, zero-downtime path. Cognito is architecturally different (SRP, no server-side plaintext-hash storage), and this distinction only surfaces once someone actually goes looking for the export mechanism. Separately, migration plans naturally get scoped around the "active" users a team can see and think about, which underrepresents the long tail of dormant accounts a full user-pool export actually contains.

**How to avoid:**
Plan one of two proven patterns from day one, not as a fallback discovered late, and size the decision against the **true total account count from Pitfall 1**, not the GA-active subset:
1. **Shadow-auth on first login (recommended, zero forced resets, works for dormant accounts too):** Create Firebase Auth accounts for all users up front with no password set, keyed by email. On login, first attempt Firebase Auth; on failure, fall back to authenticating the credentials against Cognito (kept alive, read-only, for this purpose), and on success, set that same password on the Firebase Auth account via the Admin SDK and mark the user migrated. This is the only approach that doesn't require a dormant user to take any action before their next natural login, whenever that is — which matters more, not less, once the true account count (and therefore dormant-account count) is known to be larger than 259.
2. **Forced password reset for all users at cutover:** Simpler to build, but the churn/abandonment risk described above lands hardest on dormant accounts specifically, and — per Pitfall 5 — a subset of those dormant accounts may still be paying subscribers who never notice the reset email and lose access to a service they're still being billed for.
Given zero data loss is a hard constraint for the *full* account base (not just the GA-visible slice), prefer pattern 1, and budget for Cognito to remain live (read-only, auth-check-only) for a genuinely long tail post-cutover — long enough to plausibly catch even infrequent-login users, not just a few weeks sized around "active" usage patterns.

**Warning signs:** Discovering only during a `firebase auth:import --hash-algo=...` dry run that there is no hash to supply; any migration doc that says "export Cognito hashes" without naming SRP explicitly; a Cognito-decommission date set based on how long "active" users take to return, rather than a deliberately generous window that accounts for dormant accounts.

**Phase to address:** Auth-migration design phase, immediately after Pitfall 1's true-count measurement — the dormant-account tail directly determines how long Cognito must stay live post-cutover, which affects infrastructure/cost decisions for every later phase.

### Pitfall 3: Designing the new Firestore schema without first enumerating what "zero data loss" actually requires mapping from DynamoDB

**What goes wrong:**
The rebuild is free to design whatever Firestore schema fits the new app best — there is no requirement to reproduce DynamoDB's single-table/GSI shape, and doing so would import query patterns that don't fit Firestore's model anyway (see Pitfall 8). The risk is not "the new schema differs from the old one" — that's expected and good — the risk is designing that new schema **without first producing an explicit field-by-field, entity-by-entity mapping** from every existing DynamoDB attribute to its new Firestore home, and validating that mapping is total (every field a real record can contain has a defined destination, including sparse/optional/legacy fields that only some old records carry, e.g. older sheet types or fields added and later deprecated over the app's history). Skip that mapping step and it's easy to design a clean, idiomatic new schema that silently drops fields nobody thought to check for — data loss that only surfaces when a specific migrated user notices something is missing from a character they haven't opened in months.

**Why it happens:**
Schema redesign is naturally approached top-down (what does the new app need?) rather than bottom-up (what does every existing record actually contain?) — and a single-table DynamoDB design with no schema validation (`CONCERNS.md` already flags "No Input Validation Framework") means the *real* shape of stored data includes years of accumulated, undocumented field variation that isn't visible from reading the current app's code alone.

**How to avoid:**
Before finalizing the new Firestore schema, produce the mapping as an explicit, reviewed artifact: (1) sample and diff a meaningful cross-section of real DynamoDB records per `object_type` (not just the fields the current UI reads/writes, since old or dead fields may still be present in stored data) to build a true inventory of what's actually stored; (2) design the new Firestore schema for the new app's needs, as intended; (3) write the mapping from (1) to (2) explicitly, and treat any DynamoDB field with no defined Firestore destination as a decision to make consciously (migrate it into a catch-all/legacy bag field, or explicitly decide it's safe to drop and document why) rather than an oversight; (4) validate the mapping against the full record set (or a large, representative sample) during the migration dry-run (Pitfall 4), not just against a handful of hand-picked test characters.

**Warning signs:** A schema design process that starts and ends with "what does the new app's UI need," with no step that inventories real stored data; a migration script that only handles fields the new app's forms currently read/write, silently dropping anything else in the source record.

**Phase to address:** Data-model design phase, before migration tooling is built — the field-by-field mapping is a first-class, reviewed deliverable of this phase, distinct from (and prerequisite to) the new schema's own design.

### Pitfall 4: Big-bang export/import instead of a reconciled, verifiable, throughput-aware zero-data-loss cutover

**What goes wrong:**
The instinct for "migrate the data" is: freeze writes, export all DynamoDB items, transform, bulk-import into Firestore, flip DNS, done. For a live app with active paying users, this either requires real downtime (freezing writes for however long the export/transform/import takes, which grows with account count) or — if writes aren't actually frozen — creates silent data loss for anything a user saves in the gap between "export snapshot taken" and "cutover complete," with no detection mechanism, because a one-shot export has nothing to reconcile against. This risk scales directly with the true record count from Pitfall 1: both Firebase Auth's bulk-import and Firestore's bulk-write paths have real throughput ceilings that a plan sized around "259 users" will underestimate. `firebase auth:import` batches imports (roughly 1,000 accounts per underlying batch call) and can hit rate limits on very large pools; Firestore's own guidance is the "500/50/5" ramp-up rule for sustained high write rates into a new collection (start at ≤500 writes/second, grow ~50%/day, spread hot writes across enough distinct document-ID prefixes to avoid sequential-key hotspotting) — a naive "write every migrated record as fast as the script can loop" import can throttle, partially fail, or (worse) silently succeed while creating a write-hotspot on auto-incrementing/sequential document IDs if the true record count is large enough to matter, none of which shows up when testing against a small sample.

**Why it happens:**
A single export/import script is the fastest thing to build and looks complete once it runs without errors — the failure mode (data written during the migration window is lost, or throttled/dropped mid-large-import) doesn't show up in the migration script's own success/failure signal at small test scale, only against the real, larger-than-expected record count, and only in a support ticket or a partial-import audit days or weeks later.

**How to avoid:**
Build the migration as a **verifiable, resumable, idempotent, throughput-aware** process, not a one-shot script: (1) bulk backfill historical data into Firestore ahead of cutover while the AWS app remains the source of truth and fully writable, using batched writes (Firestore's 500-writes-per-batch limit) with a deliberate ramp-up rate rather than max-speed looping, and document IDs that avoid sequential hotspotting; (2) run a reconciliation pass comparing item counts and content hashes between DynamoDB and Firestore per entity, using the field-by-field mapping from Pitfall 3 as the source of truth for what "matches" means, logging and re-syncing any drift, repeatable as many times as needed with zero risk (idempotent upsert, not append); (3) only at actual cutover, put the AWS app briefly into a short, explicit read-only maintenance window (minutes, not hours) to run one final incremental sync of anything written since the last backfill pass, verify the reconciliation report is clean against the **true total record count from Pitfall 1** (not the GA-sized estimate), then flip traffic to the new Firebase app. Communicate the maintenance window to users in advance rather than pretending there is none — a short, honest window is far less risky than a silent one. Keep the DynamoDB export retained and readable for a defined post-cutover period as a rollback/audit source, not deleted on cutover day. Dry-run the full bulk-import pipeline against a realistic-scale synthetic or staging dataset (sized to the true count, not 259) before running it against production data, specifically to surface throughput/throttling issues while they're still cheap to fix.

**Warning signs:** A migration plan with no reconciliation/verification step, or one where "success" is defined as "the import script exited 0" rather than "row counts and checksums match source and target"; a bulk-import script never load-tested against anything close to the true record count; throttling/rate-limit errors appearing for the first time during the actual production migration run.

**Phase to address:** Data-migration phase — design the backfill + reconciliation + throughput-ramped + short-window cutover sequence explicitly, sized against Pitfall 1's real counts; do not let "cutover" be a single script.

### Pitfall 5: Stripe billing discontinuity during the AWS→Firebase cutover — including for dormant-but-paying subscribers invisible to usage analytics

**What goes wrong:**
Stripe billing is being kept as-is, but the app currently mediates all Stripe operations through an AWS Lambda (`FCSStripe`, invoked via Cognito-derived credentials) — customer creation, checkout, and portal-redirect all assume that specific auth/credential chain. When the identity layer moves to Firebase Auth, the new backend (Cloud Functions or equivalent, and the new implementation of this integration is free to be structured however fits best — there's no requirement to mirror the old Lambda's internals) needs its own way to (a) map an existing Stripe `customer_id` to the *new* Firebase-Auth UID for **every** subscriber in the true account base (Pitfall 1) — not just the ~259 GA-visible ones, and critically not just the ones anyone remembers to test with — and (b) continue receiving and correctly processing Stripe webhooks (subscription renewed/cancelled/payment failed) without a gap or double-processing during cutover. A subscriber who pays automatically via a saved card and never logs into the app between renewals is exactly the profile GA's active-user count misses entirely, yet their subscription keeps renewing and their `customer_id`↔account mapping still must be correct on the very first renewal event that fires after cutover — if that mapping was built only from a "known active users" list rather than a full Stripe customer export cross-referenced against every Cognito/DynamoDB account, these dormant-but-paying accounts are the ones most likely to be missed, and the failure mode (a renewal event with no matching account, or a cancellation that never reaches an account because it isn't in the mapping table) is silent until the subscriber notices a billing or access problem weeks later. If the webhook endpoint moves from the old Lambda URL to a new Cloud Function URL as part of the same cutover as the auth/data migration, and the two aren't sequenced carefully, a renewal or cancellation event that fires during the transition window can also be missed entirely or processed twice (double-charge risk if the handler isn't idempotent on Stripe's event ID).

**Why it happens:**
Billing is explicitly "kept as-is" so it's easy to treat as out of scope for the migration — but "the billing product stays the same" is a different claim from "the code path that talks to Stripe stays the same," and the latter is exactly what's being rebuilt. Separately, any migration-scoping exercise that starts from "our users" tends to start from the most visible/active list, which is precisely the list that under-represents auto-renewing-but-quiet subscribers.

**How to avoid:**
Treat the Stripe integration as its own migration sub-plan, sequenced explicitly relative to the auth/data cutover, and scoped against Stripe's own customer/subscription list — not against GA or any "known active users" list: (1) pull the authoritative subscriber list directly from Stripe (every customer with an active or recently-active subscription), and require every one of them to have a confirmed row in the Cognito→Firebase-UID mapping before cutover — treat any Stripe customer without a matching mapped account as a blocking data-quality issue to resolve, not an edge case to skip; (2) build the new Cloud Function Stripe integration (in whatever structure fits the new backend best) and point Stripe's webhook config at it *before* cutover, running it in parallel/shadow mode against the old Lambda (both receive the webhook, only the old one acts) to prove correctness without risk; (3) build the Firebase-UID ↔ Stripe-customer-ID mapping as part of the same user-migration step from Pitfall 2 (every migrated user row must carry their existing `customer_id` forward — do not rely on email-based re-lookup as the only source of truth, since email changes happen); (4) make the new webhook handler idempotent on Stripe's `event.id` before it goes live, so a re-delivered or dual-received event during the cutover window is a no-op, not a double charge or double grant; (5) cut the webhook endpoint over atomically (Stripe dashboard config change) at the same moment as the maintenance window from Pitfall 4, not before the data migration is verified and not after (a mismatched interval where the new backend is live but the webhook still points at the decommissioned Lambda silently drops billing events).

**Warning signs:** Any subscriber reporting "I was charged but lost access" or "I cancelled but I'm still being billed" in the weeks after cutover — treat immediately as a migration defect, not user error, and check for un-mapped `customer_id` or duplicate/missed webhook events first; a Stripe customer count that doesn't reconcile against the mapped-account count before cutover.

**Phase to address:** Billing-continuity phase, planned alongside (not as a side effect of) the auth-migration and data-migration phases; scoped from Stripe's own customer list per Pitfall 1's true-count discipline; webhook cutover is part of the same maintenance-window sequencing as Pitfall 4.

### Pitfall 6: The Rewrite Trap — scope creep beyond the two hard constraints, and an extended "dark period" with no shippable increments

**What goes wrong:**
"Rebuild from scratch, and the old architecture doesn't need to be preserved" is correct and freeing, but it also removes the natural discipline an in-place migration has (the app must stay releasable, and every changed line maps to a known old behavior). Two failure modes follow: (a) scope creep past the two hard constraints — every improvement idea, new game system, or feature idea starts to feel justified "since we're rebuilding anyway," growing the surface area past what functional/print parity and zero data loss actually require; (b) a long period where the old app is the only shippable thing and the new app accumulates months of unreleased, unvalidated work before its first real user ever touches it — the riskiest possible delivery shape for a solo maintainer, since the first real contact with users and real migrated data also becomes the highest-stakes moment (full cutover). `PROJECT.md` already scopes v2.0 to 12 game systems, campaigns/scenes/adversaries CRUD, dice roller, P2P VTT, Stripe, and full-user-base migration — parity with that surface (however it's implemented underneath), not an expanded one, is the actual deliverable.

**Why it happens:**
Freedom to redesign internals is easy to conflate with freedom to redesign *scope* — "we don't have to keep the old `getVal`/`setVal` pattern or the old DynamoDB schema shape" is true and good; "we don't have to keep the old feature set fixed" is a different and much riskier claim that can creep in unnoticed under the same "greenfield" banner.

**How to avoid:**
Hold the two hard constraints (functional + print-fidelity parity; zero data loss for the full user base) as the only non-negotiable definition of "done" for v2.0, while leaving every implementation decision genuinely open. Concretely: (1) track a parity checklist derived from the current app's actual feature surface (12 sheet types, campaigns/scenes/adversaries CRUD, dice roller, VTT, Stripe) and treat anything not on that list as out of scope for v2.0, regardless of how tempting it is mid-rebuild — new architecture, new patterns, and reasonable UI polish are fine; new *features* are not, unless explicitly re-scoped; (2) sequence the rebuild so the highest-risk, most load-bearing pieces ship and get real signal first — print-fidelity sheet rendering and the data-migration mechanics (Pitfalls 1–5) should be de-risked with real subscriber data as early as possible, not held until the end as "integration work"; (3) use a parallel-run/soft-launch strategy rather than a single cutover: stand the new Firebase app up on a separate subdomain or behind a feature flag, invite a small subset of consenting existing users to use it against real migrated data while the old AWS app keeps serving everyone else, and widen the rollout once that cohort's usage surfaces gaps solo testing won't catch; (4) explicitly track "parity gaps" as a visible list throughout the rebuild (verified-working vs. not-yet-verified against the current app's user-facing behavior) rather than discovering gaps only at final cutover review.

**Warning signs:** "We'll do a full QA pass before cutover" as the only planned verification step; the roadmap has no phase where a real (even if small) group of actual users touches the new app before the full-base cutover; a scope addition justified with "since we're rebuilding anyway" that doesn't trace back to one of the two hard constraints.

**Phase to address:** This is a cross-cutting roadmap-structure concern, not a single phase — it should shape phase *ordering* (print-fidelity and migration-mechanics early, not late) and should produce an explicit parallel-run/soft-launch phase before the full cutover phase, plus a maintained parity checklist scoped to the two hard constraints throughout.

### Pitfall 7: No incremental rollback path if the full cutover reveals a serious defect

**What goes wrong:**
Once DNS/traffic is flipped to the new Firebase app and users start writing new data into Firestore, "roll back to the old AWS app" is no longer simply "flip DNS back" — any data written post-cutover only exists in Firestore, so reverting to AWS/DynamoDB would itself be a data-loss event unless a reverse-sync path was built. Teams that plan the forward migration in detail but not a rollback path discover this exactly when they need it most: mid-incident, under time pressure, with paying users affected — and a rollback that itself causes data loss directly violates the zero-data-loss constraint just as much as a forward-migration bug would.

**Why it happens:**
Rollback planning is deprioritized because it "shouldn't be needed" if the forward migration is done right — but the projects most likely to need a documented rollback are exactly the ones confident enough to skip planning one.

**How to avoid:**
Define, before cutover, an explicit rollback decision window and mechanism: for a short period post-cutover (hours, not days), keep the old AWS stack fully intact and capable of receiving traffic again, and decide up front what "roll back" means for data written during that window (accept a small window of reconciliation work re-syncing Firestore writes back to DynamoDB if rollback is triggered, rather than discovering there's no plan for it). After the rollback window closes and the migration is confirmed stable, decommission AWS resources on a deliberate schedule (not immediately) — cost of keeping Cognito/DynamoDB alive a few extra weeks is trivial compared to the cost of an unrecoverable incident.

**Warning signs:** No documented answer to "what do we do if a critical bug is found 6 hours after cutover with real post-cutover writes already in Firestore" before cutover day arrives.

**Phase to address:** Cutover phase — the rollback plan is a deliverable of this phase, reviewed and signed off before the maintenance window from Pitfall 4 opens, not written reactively during an incident.

### Pitfall 8: Designing a Firestore schema that can't actually serve the app's real query needs (the flip side of freedom to redesign)

**What goes wrong:**
Because the new schema doesn't need to reproduce DynamoDB's GSI-backed access patterns (`type`, `related_id`, `id` indexes used today for cross-owner lookups like public campaign/adversary browsing), it's tempting to design Firestore collections purely around "what's clean" without checking they can still serve every real access pattern the current app needs for functional parity. Firestore has real, different constraints of its own: no `OR` across different fields in one query (its `OR`/`in` support is narrower than DynamoDB's filter expressions — it works within a single field's set of values, not arbitrary field combinations), no query across multiple top-level collections except via collection-group queries (which only work if sub-collections share a name), and every compound/sorted query needs a composite index defined ahead of time — an un-indexed compound query fails outright at request time with a console error (good, since it's loud, not silent — but only if discovered before cutover, not after).

**Why it happens:**
"We're free to design this however we want" easily slides into designing the schema before checking it against the actual list of queries the current app performs — and Firestore's restrictiveness (by design, so every query is guaranteed indexed and cheap at scale) means a schema that looks clean on paper can still fail to serve a real feature.

**How to avoid:**
Enumerate every real query the current app performs (character list by owner, public campaign browse, adversary search-as-you-type, scene lookup by id cross-owner, session/campaign filter search) as an explicit list during the data-model design phase — this list is the functional-parity contract, not a legacy constraint — and validate each one against the *new* schema's actual Firestore query capabilities before committing to it, using collection-group queries and denormalized `public`-style flags where a DynamoDB GSI pattern needs a Firestore-idiomatic equivalent. For the search-as-you-type patterns specifically (currently client-side JS filtering over an already-loaded list per `CONCERNS.md`), decide explicitly whether Firestore's limited text-search (`>=`/`<=` prefix queries only, no full-text search) is sufficient for parity, or whether a dedicated search product (Algolia/Typesense, commonly paired with Firestore via a sync extension) is needed to preserve the current search experience.

**Warning signs:** A composite-index-required error surfacing for the first time against production data after cutover rather than during development; a feature that worked in the old app (e.g., public adversary browsing) quietly missing or degraded in the new app because the schema wasn't checked against that query before launch.

**Phase to address:** Data-model design phase (enumerate queries, validate against the new schema) and a dedicated Firestore indexes review before the parallel-run/soft-launch phase (Pitfall 6) — indexes should be committed to source control (`firestore.indexes.json`) and deployed alongside rules, never created ad hoc via the console in production.

### Pitfall 9: Firestore security rules become the *entire* server-side authorization boundary — there is no equivalent of Cognito-scoped IAM credentials unless one is deliberately built

**What goes wrong:**
Today, every DynamoDB call from the browser goes through short-lived AWS credentials obtained via Cognito Identity Pool, scoped by an IAM role (`FateCharacterSheetUser`) — server-side AWS enforces the access boundary regardless of what the frontend code does. If the Firebase rebuild uses the Firestore client SDK directly from the browser (the natural, idiomatic Firebase pattern), **Firestore security rules become the only thing standing between an authenticated user and any other user's data** — there is no IAM-role-equivalent safety net behind it. The old codebase has known, documented gaps here (`CONCERNS.md` flags "No Input Validation Framework" and a bug where "Subscription Check Missing in Host Validation" lets any authenticated user act as scene host regardless of subscription tier) — these are exactly the kind of known-broken behaviors the rebuild should fix, not carry forward. A rule that checks `request.auth != null` but not `request.auth.uid == resource.data.owner_id`, or one that checks ownership on read but not on the `owner_id` field itself being immutable/self-assigned on write, would reproduce or worsen those old gaps in the new stack — and Firestore rules failing open is a direct, immediate, full-collection data exposure, not a latent bug, affecting the entire true (larger than GA-visible) user base from Pitfall 1.

**Why it happens:**
Security rules read like client-side validation (declarative, easy to under-specify) but function as server-side authorization (must be adversarially complete) — teams moving from a model where AWS enforced the boundary underestimate how much rigor Firestore rules need to carry alone.

**How to avoid:**
Write Firestore rules defensively and testably from the start — this is one of the clearest opportunities in the whole rebuild to fix a known-broken old behavior rather than reproduce it: every collection needs (a) a read rule scoped to `resource.data.owner_id == request.auth.uid` OR an explicit `public == true` flag for shared entities (never just `request.auth != null`), (b) a create rule that binds `owner_id`/subscription-tier fields to values the rules themselves derive from `request.auth`, not values the client supplies in the write payload (prevents the "user sets their own owner field" escalation), and (c) an update rule that re-validates immutable fields (`owner_id`, entity type) haven't been changed by diffing `resource.data` vs `request.resource.data`. Use the Firestore emulator + `@firebase/rules-unit-testing` to write actual test cases for "user A cannot read/write user B's character," "non-subscriber cannot act as scene host" (explicitly closing the old bug), and similar — treat rules tests as load-bearing regression tests, not optional. For genuinely privileged operations that need server-side business logic beyond what rules can express (subscription-tier gating, the Stripe-adjacent operations currently in the `FCSStripe` Lambda), use Cloud Functions (callable functions), structured however fits the new backend best.

**Warning signs:** Any Firestore rule that only checks `request.auth != null` without also scoping to a specific owner/uid field; no automated rules tests exist; a manual test of "can user A see user B's private character by guessing/enumerating IDs" was never performed; the old app's "Subscription Check Missing in Host Validation" bug reappearing in the new rules.

**Phase to address:** Security-rules design phase, done alongside the data-model phase (Pitfall 3/8) and verified with automated emulator tests before the parallel-run/soft-launch phase — this is not a "harden later" item, since a permissive rule is a live data-exposure risk from the first real user onward.

### Pitfall 10: Firestore cost surprises from real-time listeners and per-document read billing at scale

**What goes wrong:**
Firestore bills per document read/write/delete, not per query — a listener (`onSnapshot`) that attaches to a collection charges for every document in the initial result set on connect, and (if offline persistence isn't configured) re-charges for the full result set on every reconnect (network drop, tab wake, mobile backgrounding). The VTT/scene feature is exactly the kind of high-frequency, real-time, multi-document-update workload that inflates Firestore bills the fastest if it's implemented as Firestore listeners rather than the peer-to-peer channel the app already uses for that purpose. Unlike DynamoDB (where the current app is on-demand/pay-per-request but with a known, bounded access pattern), Firestore has **no hard spending cap on reads/writes** — only after-the-fact GCP billing budget *alerts*, which notify but do not stop usage — so a bug that causes a listener storm (e.g., a component re-subscribing on every re-render instead of once) can run up real cost before anyone notices, not just degrade performance. This risk is also directly sensitive to the true account count from Pitfall 1: cost projections built against 259 GA-active users will underestimate the actual read/write volume if the true base (and therefore concurrent-usage ceiling) is larger.

**Why it happens:**
Firestore's real-time listener API is easy to reach for anywhere "live-updating UI" is needed, and its cost model (per-document, not per-query, not flat-rate) is invisible in day-to-day development against the free tier/emulator — it only becomes visible in a production bill weeks later.

**How to avoid:**
Keep the VTT's real-time transport on PeerJS (peer-to-peer), as already planned — do not re-architect live scene/dice/invoke messaging onto Firestore listeners; Firestore should hold durable state (character sheets, campaign/scene records), not high-frequency ephemeral messaging. Where Firestore listeners genuinely are used (e.g., live character-sheet sync across tabs), scope them narrowly (`doc()` listeners on a single character, not `collection()` listeners over a whole list) and unsubscribe deterministically on component unmount. Set a GCP billing budget alert at a conservative threshold from day one of the Firebase project (not after the first surprising bill), and load-test the highest-fan-out real read pattern (e.g., public campaign/adversary browsing) against the true registered-user count from Pitfall 1, not the smaller GA-active figure, before the full cutover.

**Warning signs:** Any component that calls `onSnapshot` in a reactive/render path (re-subscribing on every update) rather than once with an explicit unsubscribe on teardown; a GCP bill with a read-count that doesn't correlate with active-user count.

**Phase to address:** Architecture-decisions phase (VTT stays on PeerJS, not Firestore listeners) and a cost-guardrail step (billing alerts, listener-scope review, cost projection re-based on Pitfall 1's true counts) before the parallel-run/soft-launch phase.

### Pitfall 11: Print-fidelity regressions from the framework/CSS/font stack change, discovered only after the visual redesign is "done"

**What goes wrong:**
Print-fidelity is one of the two hard constraints for this rebuild, but print rendering is exactly the kind of thing that "looks fine on screen" while silently degrading in the one output mode (physical paper / print-to-PDF) that matters most: `@media print` page-break behavior differs meaningfully between Chromium and Firefox print engines (page-break-inside/before/after interacting unpredictably with flex/grid layouts, which any modern rebuild will likely use more of than the current app's Bootstrap-4-grid approach), web fonts can substitute or fail to embed correctly in print/PDF output depending on `@font-face` and print-CSS handling, and a from-scratch layout redesign — genuinely free to differ from the old fixed-pixel sheet layouts — still needs deliberate print-specific rules, since good screen-responsive layout doesn't automatically translate to correct print output. Because the new stack is unknown/open per `PROJECT.md` ("framework is open... judged on print-fidelity sheet rendering"), there's a real risk of picking a framework/component-library for its screen-rendering DX and only validating print output late, after the visual design is otherwise "done" and hard to unwind.

**Why it happens:**
Print CSS is a secondary concern in almost every modern frontend framework/tooling ecosystem (screen-first is the default assumption everywhere from CSS resets to component libraries), so it's easy for print fidelity to become the very last thing verified rather than a design constraint checked continuously.

**How to avoid:**
Treat print-fidelity as a first-class, continuously-verified hard constraint rather than a final QA pass: (1) when selecting the frontend framework/stack, explicitly build and print-test (real printer output, not just print-preview) at least one representative character sheet early, before the framework choice is locked in — this should directly gate the stack decision, per `PROJECT.md`'s own framing; (2) establish print-specific CSS from the start (`@page` rules, explicit `break-inside: avoid` on sheet sections, points/inches units for print-specific stylesheets rather than reusing screen `rem`/`vw` values) as a deliberate design decision in the new layout, not an afterthought; (3) test print output across the actual browsers real users print from (Chrome and Firefox at minimum, since page-break support differs), not just the maintainer's default browser; (4) if any part of the print path (e.g., PDF export) is added or changed, verify font embedding explicitly — a font that renders correctly on-screen via a CDN/web-font can silently fall back to a system font in print/PDF if not embedded correctly.
Given "solo maintainer, Windows dev environment" — budget real time for physical-printer or print-to-PDF verification on Windows specifically (font rendering and print dialogs behave differently across OSes), not just relying on a Mac/Linux CI screenshot diff.

**Warning signs:** Print-fidelity verified only via on-screen "print preview" rather than actual print/PDF output; the framework decision finalized before any print test was run; a sheet that "looks pixel-perfect on screen" but breaks mid-section across a page boundary or substitutes a fallback font when printed.

**Phase to address:** Stack-selection phase (print-fidelity as a hard gate on the framework decision, tested early) and its own explicit print-verification phase/checklist before considering any sheet type "done," repeated for all 12 sheet types, not just one.

### Pitfall 12: PeerJS signaling on Cloud Run breaks mid-session from scale-to-zero and session-affinity limits, in ways the current Heroku dyno doesn't

**What goes wrong:**
The current PeerJS signaling server runs on a persistently-running Heroku dyno with a stable connection. Cloud Run (the natural Firebase-family fit for "persistent WebSockets," per `PROJECT.md`'s own framing) is fundamentally a **request-scoped, autoscaling** compute model: a WebSocket connection must stay pinned to one instance for its entire life (session affinity), that affinity is *best-effort* and can break during scaling events, request/connection duration is capped, and — critically — if Cloud Run scales an instance down (including to zero on an idle service, which is the default and the main cost-saving reason to use Cloud Run at all) **any WebSocket connections on that instance are terminated**. A live game session's signaling connection dying mid-session because the container was reclaimed for being "idle" between VTT-sends (chat/dice-roll/invoke messages are bursty, not constant, so a Cloud Run instance can look idle between them) is a materially different and worse failure mode than what the app has today — a functional-parity regression against hard constraint #1.

**Why it happens:**
"Move it to Cloud Run" is an easy first instinct because Cloud Run is the flagship "run any container" product in the Firebase/GCP family, but it's tuned for stateless HTTP request/response workloads — a long-lived stateful WebSocket signaling server is closer to a "keep a server running" workload than a "handle a request" workload, and Cloud Run's autoscaling defaults actively work against that unless explicitly configured otherwise.

**How to avoid:**
If Cloud Run is used for the PeerJS signaling server, configure it deliberately for this workload rather than accepting defaults: set a **minimum instance count of 1** (disables scale-to-zero, at a small but real always-on cost — budget for this rather than being surprised by it), enable session affinity explicitly, and keep concurrency per instance conservative and tested against the app's actual peak concurrent-scene count (currently ~10-50 players per scene per `CONCERNS.md`'s own scaling-limits note). Load-test a real multi-hour VTT session against the Cloud Run deployment (not just a smoke test) before relying on it for real games, specifically watching for connection drops during idle-then-burst patterns (a GM setting up a scene, then a burst of dice rolls). If reliability testing surfaces problems that persist even with min-instances=1, evaluate Cloud Run's newer WebSocket/streaming support maturity at build time (this is an actively evolving area of the platform) against alternatives explicitly built for this pattern (e.g., a small persistently-running Compute Engine/App Engine flex instance, or keeping the PeerJS server off Cloud Run entirely and only moving the parts of the stack that are genuinely stateless) — do not assume "Firebase-family" requires everything to run on Cloud Run specifically.

**Warning signs:** A live-play session where players report the game "randomly disconnects" after a period of inactivity followed by a burst of activity; no minimum-instance configuration set, relying on default scale-to-zero.

**Phase to address:** VTT-infrastructure phase — this needs its own explicit reliability validation step (multi-hour load test with realistic burst/idle patterns) before the PeerJS signaling migration is considered done, sequenced independently of the print-fidelity and data-migration work since it's an orthogonal risk area.

### Pitfall 13: Solo-maintainer overengineering — rebuilding "properly" into something harder to maintain than what it replaced

**What goes wrong:**
A greenfield rebuild is the classic moment a solo maintainer over-corrects for every pain point in the old codebase at once — modular state-store architecture, a full DI/service-container framework, TypeScript strictness across the board, a microservices-flavored Cloud Functions split, a component library chosen for theoretical flexibility over practical fit — each individually reasonable, collectively producing a new codebase that is more architecturally sophisticated than one person can keep in their head and maintain solo. Related and compounding: choosing dependencies for the new stack that are new/trendy but thinly maintained (a solo maintainer inherits 100% of the risk if a chosen library goes unmaintained, since there's no team to absorb a forced migration later), and Windows-specific tooling friction (some Firebase-ecosystem and Node-native-binding tooling has historically had rougher edges on Windows than macOS/Linux — WSL2 is the common mitigation but adds its own environment-parity considerations for a Windows-primary dev setup).

**Why it happens:**
"We're rebuilding anyway, and nothing about the old architecture is sacred" creates permission to relitigate every architectural decision at once — which is exactly the freedom this rebuild correctly grants — but it's hard to distinguish "this genuinely needs fixing" from "this bothered me and now I have an excuse" in the moment, especially without a second person to push back.

**How to avoid:**
Set an explicit, written complexity budget before starting: prefer boring, widely-adopted, actively-maintained dependencies (checked for recent commit activity/maintainer responsiveness, not just star count) over "best in theory" ones; keep state management as simple as the app's actual needs require; resist introducing a service-container/DI framework unless a concrete, current pain point demands it rather than "it's more correct." Validate the target stack on the actual Windows dev machine *early* (framework CLI install, dev server hot-reload, Firebase emulator suite, any native-binding dependencies) as part of the stack-selection phase, not discovered as friction mid-build. When evaluating a new library, explicitly check its Windows-support status and last-release recency as part of the same evaluation as its features — a library that's a great technical fit but effectively unmaintained is a worse bet for a solo maintainer than a slightly-less-ideal but actively-maintained alternative, because there's no team to fork/patch/replace it under time pressure later.

**Warning signs:** A stack-decision doc that reads like a resume-driven-development wishlist rather than a fit-for-purpose list; any dependency chosen without checking its maintenance status; discovering a Windows-specific tooling blocker after the stack is already partially built out rather than during initial setup.

**Phase to address:** Stack-selection/setup phase — write the complexity budget and dependency-maintenance criteria down before evaluating options, and smoke-test the full toolchain on Windows as an explicit setup-phase exit criterion, not an assumption.

## Performance Traps

| Trap | Symptoms | Prevention | When It Breaks |
|------|----------|------------|----------------|
| Collection-wide `onSnapshot` listeners on lists (character list, campaign list) instead of scoped/paginated queries | Firestore read cost grows faster than active-user count; UI feels fine at low scale, bill doesn't | Scope listeners to what's actually rendered (paginate, or use one-time `get()` for list views and reserve `onSnapshot` for the single open document) | Noticeable in billing once past a few dozen active users with list-heavy usage; invisible below that, and more likely once real usage matches the true (larger) account base rather than the GA-visible one |
| Un-indexed compound queries only discovered against production data | Feature works in dev against small/simple test data, fails with a console error against real query combinations post-cutover | Enumerate and index every real query shape (Pitfall 8) before the parallel-run phase, test against migrated real-scale data, not synthetic dev fixtures | Breaks the first time a real user's data triggers a query shape not exercised in dev testing |
| Bulk-import script run at unthrottled speed against the true (possibly much larger than 259) record count | Throttling/rate-limit errors, partial imports, or write hotspotting mid-migration | Batch, ramp, and load-test the import pipeline against realistic scale before the real run (Pitfall 4) | Breaks specifically once real record volume exceeds whatever the script was tested against — a script that "worked fine" on a 259-row test sample is not evidence it works at true scale |
| Cloud Run cold starts on the PeerJS signaling server if min-instances isn't set | First player to join a scene after a quiet period experiences a multi-second connection delay or outright failure | Min-instances ≥ 1 for the signaling service (Pitfall 12) | Immediately noticeable to real users; won't show up in a quick manual smoke test done back-to-back |
| Large scene canvas (existing 4800×3600px fixed canvas, all objects rendered) reproducing the same rendering ceiling in the new stack without deliberate improvement | Same memory/render performance ceiling as today (~500 objects per `CONCERNS.md`) carried forward into the rebuild by default | Since the rebuild already touches this component and isn't constrained to reproduce the old implementation, address viewport culling/virtualization as a deliberate design choice rather than defaulting to the old ceiling | Same threshold as today — large scenes on lower-end/mobile devices, unless addressed |

## Security Mistakes

| Mistake | Risk | Prevention |
|---------|------|------------|
| Firestore rules that check `request.auth != null` without also scoping to `resource.data.owner_id == request.auth.uid` | Any authenticated user (including a free/trial account) can read or write any other user's private character/campaign data — a full data breach across the entire true account base, not a latent bug | Write and automated-test every rule against "user A cannot access user B's data" scenarios using the Firestore emulator before any real data is exposed (Pitfall 9) |
| Allowing the client to set its own `owner_id`/subscription-tier field on document create | A user can self-assign ownership of arbitrary documents, or self-grant subscriber-only privileges (the same category of gap as the old app's documented "Subscription Check Missing in Host Validation" bug, now as a security-rules gap instead of a missing app-level check) | Bind privileged fields to values the rule itself derives from `request.auth`/a server-controlled subscription-status document, never trust `request.resource.data` for these fields |
| Reintroducing an `eval()`-based or otherwise unsafe dynamic path-access pattern in the new codebase because "it's a known, working approach" | Same arbitrary-code-execution risk already flagged Critical in `CONCERNS.md` for the old app, now baked into a brand-new codebase from day one instead of being retired as intended | Use a safe, typed path-accessor or direct property access in the new implementation — this is exactly the kind of known-broken old behavior the rebuild should fix, not carry forward |
| Treating Firebase Hosting's default open CORS/rewrite config, or a Cloud Function's default auth posture, as equivalent to "credentials scoped by IAM role" from the old stack | A callable Cloud Function or HTTP endpoint left without its own auth check is reachable by anyone, not just authenticated app users — there's no IAM-role backstop like the current Cognito Identity Pool → scoped role chain provided | Explicitly verify auth (`context.auth`) inside every Cloud Function that touches user data or billing, don't assume network-level restriction exists by default |
| Exporting Cognito/Stripe data for the migration (Pitfall 1's count query, Pitfall 5's customer export) and leaving the resulting flat files (emails, hashed-or-not credentials, customer IDs) sitting in an unsecured location during the migration project | A bulk export of the full account base is a much richer target than the running production systems it was pulled from — accidental exposure (committed to a repo, left in an open bucket) is a full user-base breach | Treat migration export files as sensitive artifacts from creation: store them in an access-controlled location, never commit them to source control, and delete them once the migration is verified complete and the rollback window (Pitfall 7) has closed |

## UX Pitfalls

| Pitfall | User Impact | Better Approach |
|---------|--------------|-------------------|
| Forced password reset at cutover with no advance warning, especially for dormant accounts | A paying subscriber tries to log in post-cutover (possibly for the first time in a long while), can't, doesn't understand why, and may churn or file a support ticket instead of resetting — or never returns at all and simply keeps being billed with no way in | Prefer the shadow-auth fallback (Pitfall 2); if a reset is ever unavoidable, email advance notice with a clear reason and a working reset link tested end-to-end beforehand, sent to the full account base, not just recently-active addresses |
| Silent maintenance-window downtime during the final data-sync cutover | Users mid-session lose unsaved work or see a confusing error with no explanation | Communicate the maintenance window in advance (in-app banner + email to the full account list), keep it short (Pitfall 4), and show a clear "we're migrating, back shortly" state rather than a generic error |
| Print output that looks correct on screen but is subtly wrong on paper (fonts, spacing, page breaks) discovered by users at the table, not by the maintainer | The exact core-value promise of the product ("looks like the printed sheet") silently breaks for the group of users who most rely on it — physical-table players | Continuous print-fidelity verification throughout the build (Pitfall 11), not a final pre-launch check |
| VTT session drops mid-game due to Cloud Run connection termination | A GM and players lose game state/connection during a live session with no warning, worse than any failure mode the current Heroku-hosted signaling server has | Reliability-test realistic session patterns before relying on Cloud Run for this (Pitfall 12); consider a visible reconnect/retry UX regardless, since P2P connections can drop for many reasons |

## "Looks Done But Isn't" Checklist

- [ ] **True scale known:** "We migrated 259 users successfully" is not the same as "we migrated the full user base successfully" — confirm the real Cognito user-pool count and distinct-`owner_id` DynamoDB count were measured and used to size the migration, not the GA-active figure (Pitfall 1).
- [ ] **Auth migration:** "Users can log in on the new app" verified with a *test* account is not the same as verifying the shadow-auth fallback against a *real*, previously-Cognito-only, ideally-dormant user's actual password — test with at least one real migrated credential from a low-activity account end-to-end, not just newly-created or recently-active Firebase accounts.
- [ ] **Data migration mapping:** "The schema looks clean and the app works against it" does not mean zero data loss — confirm a field-by-field mapping was validated against a real sample of stored DynamoDB records (not just fields the current UI reads), and that any dropped legacy field was a documented, deliberate decision, not an oversight (Pitfall 3).
- [ ] **Data migration execution:** "The import script ran without errors" does not mean zero data loss — verify with an explicit reconciliation report (counts + content hashes) comparing DynamoDB and Firestore per entity type, checked against the true total record count, not just a successful exit code (Pitfall 4).
- [ ] **Firestore security rules:** "It compiles and the app works for me" does not mean the rules are secure — run the actual emulator-based "can user A read/write user B's data" test suite before trusting rules with real data (Pitfall 9).
- [ ] **Stripe continuity:** "Checkout works in test mode on the new stack" does not mean billing continuity for existing subscribers — verify the customer_id↔UID mapping covers 100% of Stripe's own customer list (not just app-active users) and confirm webhook idempotency, plus what happens to an in-flight renewal/cancellation during the exact cutover window (Pitfall 5).
- [ ] **Print fidelity:** "It looks right in print preview" does not mean it prints correctly — verify against actual printed output (or print-to-PDF with font embedding checked) across at least Chrome and Firefox, for every one of the 12 sheet types, not just one representative sheet (Pitfall 11).
- [ ] **PeerJS/VTT on Cloud Run:** "A quick two-person test session worked" does not mean it's production-ready — load-test a longer session with realistic idle/burst patterns and confirm min-instances/session-affinity config, since cold-start and scale-down failures won't show up in a short smoke test (Pitfall 12).
- [ ] **Rollback readiness:** "We have backups" does not mean there's a working rollback plan — confirm there's an explicit, rehearsed answer for "what do we do if a critical defect is found N hours after cutover with real post-cutover writes already in Firestore" (Pitfall 7).

## Recovery Strategies

| Pitfall | Recovery Cost | Recovery Steps |
|---------|----------------|-----------------|
| Migration sized off the GA figure, true scale discovered mid-project to be much larger | LOW–MEDIUM if caught early | Re-run the Cognito/DynamoDB count query, re-baseline timelines/throughput/cost estimates immediately; cheap if caught during planning, expensive if discovered mid-bulk-import (see below) |
| Cognito password hashes can't be migrated, discovered mid-project | MEDIUM | Fall back to the shadow-auth-on-first-login pattern (Pitfall 2); requires keeping Cognito alive longer than planned, but no user-facing data loss if caught before cutover |
| New Firestore schema found to be missing real stored fields after design is "finalized" | MEDIUM–HIGH | Extend the field-mapping (Pitfall 3) to cover the gap, re-run the migration for affected entities; cost scales with how much was already built against the incomplete schema — cheaper the earlier it's caught |
| Bulk-import throttled/partially failed mid-run against the true (larger-than-planned) record count | MEDIUM–HIGH | Re-run the reconciliation pass (Pitfall 4) to identify exactly which records didn't land, resume the batched/ramped import for just the gap — recoverable without data loss only if the import was idempotent and a reconciliation step exists; if it wasn't, this becomes a much harder manual audit |
| Data loss/drift discovered post-cutover from a big-bang migration with no reconciliation | HIGH | If DynamoDB export was retained (Pitfall 4's recommendation), reconstruct missing records from it; if not retained, the loss may be unrecoverable — this is the single highest-cost recovery scenario in this project, which is exactly why the retained-export + reconciliation-report prevention is non-negotiable |
| Stripe webhook events missed or double-processed during cutover, or dormant-but-paying subscribers found unmapped post-cutover | MEDIUM | Reconcile against Stripe's own event log and full customer list (Stripe retains and allows replaying webhook events for a period) to detect and correct missed/duplicate processing or unmapped accounts; requires the new handler to be idempotent before replaying |
| Firestore security rule gap discovered after real user data is exposed | HIGH | Immediately tighten the rule; audit Firestore access logs for any exploitation during the exposure window; notify affected users if cross-account data access is confirmed — this is a real security-incident response, not a routine bug fix |
| PeerJS/Cloud Run sessions dropping in production | LOW–MEDIUM | Set min-instances ≥ 1 and enable session affinity if not already set (often resolves it); if the platform genuinely can't support the workload reliably, fall back to a persistently-running Compute Engine/App Engine flex instance for signaling specifically, keeping the rest of the stack on Firebase |

## Pitfall-to-Phase Mapping

| Pitfall | Prevention Phase | Verification |
|---------|-------------------|----------------|
| Migration sized off GA-active figure, not true account/record count (Pitfall 1) | Migration-design phase, first step | Real Cognito user-pool count and distinct-`owner_id` DynamoDB count obtained and used to re-baseline every other migration estimate |
| Cognito password hashes can't be exported, dormant-account risk (Pitfall 2) | Auth-migration design phase | Shadow-auth flow tested end-to-end against at least one real, low-activity/dormant credential, not just recently-active test accounts |
| New schema designed without a field-by-field zero-data-loss mapping (Pitfall 3) | Data-model design phase | Explicit mapping document reviewed, validated against a real sample of stored DynamoDB records (not just current-UI fields), before migration tooling is built |
| No reconciliation/throughput planning on data migration (Pitfall 4) | Data-migration phase | Reconciliation report (counts + hashes) clean for 100% of entities against the true total record count, with bulk-import pipeline load-tested at realistic scale, before the cutover maintenance window opens |
| Stripe billing discontinuity, dormant-but-paying subscribers (Pitfall 5) | Billing-continuity phase (parallel to auth/data migration) | Webhook handler shadow-verified idempotent; 100% of Stripe's own customer list confirmed mapped to a migrated Firebase UID, not just app-active users |
| Rewrite trap — scope creep beyond the two hard constraints, no shippable increments (Pitfall 6) | Roadmap structure (cross-cutting) | A maintained parity checklist scoped to functional/print parity + zero data loss; a parallel-run/soft-launch phase with real (even if few) users exists before the full-cutover phase |
| No rollback path post-cutover (Pitfall 7) | Cutover phase | Documented, reviewed rollback plan exists and is signed off before the maintenance window opens |
| New Firestore schema can't serve real query needs (Pitfall 8) | Data-model design phase + indexes review | `firestore.indexes.json` covers every enumerated query; no console-discovered missing-index errors, no missing features, during the parallel-run phase |
| Security rules lack owner scoping (Pitfall 9) | Security-rules design phase | Emulator-based rules test suite (cross-user access denial, field-tampering prevention, old-bug-class checks) passes before any real data is exposed |
| Firestore cost surprises (Pitfall 10) | Architecture-decisions phase (VTT stays on PeerJS) + cost-guardrail step | Billing budget alert configured; no collection-wide listeners in list-view components; VTT messaging confirmed off Firestore; cost projections re-based on true account count |
| Print-fidelity regressions (Pitfall 11) | Stack-selection phase (gate) + dedicated print-verification phase | Real printed/PDF output verified across Chrome and Firefox for all 12 sheet types, not print-preview only |
| PeerJS on Cloud Run reliability (Pitfall 12) | VTT-infrastructure phase | Multi-hour realistic load test with idle/burst patterns passes with min-instances/session-affinity configured |
| Solo-maintainer overengineering (Pitfall 13) | Stack-selection/setup phase | Written complexity budget exists; full toolchain smoke-tested on the actual Windows dev machine as a setup exit criterion |
